# Vision

Документ фиксирует техническое видение проекта "Chisto Prosto". Основа: текущий MVP и архитектурное эссе `Архитектура/SysArch_TechPred_exam_Станкевичус_2026_эссе.docx`.

Главный принцип: развивать продукт итерационно, сохраняя KISS. Архитектурное эссе задает целевое направление, но текущая реализация остается простым MVP без оверинжиниринга.

## 1. Цель продукта
- Цифровой агрегатор для размещения, исполнения и контроля задач по уборке городских улиц.
- Целевые пользователи: заказчики, исполнители, администраторы.
- Целевое развитие: часть цифровой инфраструктуры "умного города" с картами, уведомлениями, платежами, рейтингами, аналитикой и внешними интеграциями.
- Текущий фокус: проверка MVP-сценариев создания заказа, выбора точки уборки, назначения исполнителя и уведомления.

## 2. Технологии
- Формат: веб-приложение с адаптивным интерфейсом.
- Язык/платформа: Python.
- Бэкенд: FastAPI.
- Фронтенд: Jinja2-шаблоны, HTML, CSS, минимальный JavaScript.
- Карта: Leaflet + OpenStreetMap.
- Геокодирование: Nominatim через backend endpoint.
- База данных: SQLite.
- Email-уведомления: Resend API.
- Деплой: Render.
- Репозиторий: GitHub.

## 3. Принципы разработки
- Один сервис, одна кодовая база.
- Сначала рабочие пользовательские сценарии, потом расширение.
- Минимум зависимостей и инфраструктуры.
- Без микросервисов, брокеров, сложных очередей и преждевременной Enterprise-архитектуры.
- Архитектурные решения фиксировать простыми ADR/заметками при появлении существенных развилок.
- Документ из `Архитектура/` использовать как целевую карту развития, а не как требование реализовать все сразу.

## 4. Структура проекта
- `app/` — код приложения
  - `main.py` — роуты и основной вход FastAPI
  - `db.py` — подключение и инициализация SQLite
  - `auth.py` — регистрация, логин, роли, пароли
  - `storage.py` — работа с заказами
  - `config.py` — чтение конфигурации
  - `notifications.py` — email-уведомления
- `templates/` — HTML-шаблоны
- `static/` — стили и локальные статические файлы
- `static/vendor/leaflet/` — локальная копия Leaflet
- `data/` — локальная SQLite БД
- `doc/` — рабочие документы проекта
- `Архитектура/` — архитектурное эссе и верхнеуровневые материалы
- `.env.example` — пример конфигурации
- `.env` — локальные секреты, не коммитится
- `README.md` — запуск и настройка
- `requirements.txt` — зависимости Python

## 5. Архитектура проекта
- Тип: простой монолит.
- Слои: UI-шаблоны → FastAPI-роуты/логика → SQLite.
- Внешние сервисы:
  - OpenStreetMap/Nominatim — карта и адреса.
  - Resend — email-уведомления.
  - Render — размещение приложения.
- Роли:
  - Заказчик — создает заказ и выбирает точку уборки.
  - Исполнитель — берет заказ и отмечает выполнение.
  - Администратор — меняет статусы и фиксирует оплату.
- Асинхронные очереди не используются: внешние вызовы выполняются синхронно, ошибки логируются и не ломают создание заказа.

## 6. Модель данных MVP
- `User`: id, username, role, password_hash, salt.
- `Order`: id, address, description, price, status, assignee, paid, latitude, longitude.
- Статусы заказа: `new`, `in_progress`, `done`, `cancelled`.
- Оплата: MVP-заглушка через поле `paid`.

## 7. Реализованные сценарии
- Регистрация пользователя с ролью.
- Логин и logout.
- Создание заказа заказчиком/администратором.
- Выбор точки уборки на карте Астаны.
- Автоматическая подстановка адреса по координатам.
- Сохранение координат заказа.
- Просмотр списка заказов.
- Открытие точки заказа в OpenStreetMap.
- Взятие заказа исполнителем.
- Завершение заказа исполнителем.
- Смена статуса администратором.
- Ручная фиксация оплаты администратором.
- Email-уведомление после создания заказа.

## 8. Целевые сценарии из архитектурного эссе
- Полноценный контракт между заказчиком и исполнителем.
- Платежный контур через платежный провайдер.
- Рейтинги и отзывы.
- Аналитика и отчетность по заказам/KPI.
- Расширенная работа с исполнителями: квалификация, сертификация, история работ.
- Интеграции с городскими системами и внешними API.
- Marketplace дополнительных сервисов.

## 9. Деплой
- Код хранится в GitHub.
- Приложение размещается на Render как Web Service.
- Build command: `pip install -r requirements.txt`.
- Start command: `uvicorn app.main:app --host 0.0.0.0 --port $PORT`.
- SQLite на Render подходит для демонстрационного MVP, но не является надежным постоянным хранилищем для production.

## 10. Конфигурирование
- Настройки читаются из переменных окружения и локального `.env`.
- Секреты не коммитятся.
- Основные переменные:
  - `RESEND_API_KEY`
  - `EMAIL_FROM`
  - `NOTIFY_EMAIL_TO`
  - `APP_CONTACT_EMAIL`
- В репозитории хранится только `.env.example`.

## 11. Логгирование
- Используется стандартный `logging` Python.
- Логи пишутся в stdout/stderr и видны в Render Logs.
- Ошибки внешних сервисов логируются с деталями, но не ломают основной сценарий создания заказа.

## 12. Ближайшие архитектурные ограничения
- SQLite на Render может терять данные при пересоздании окружения.
- Nominatim имеет rate limit, поэтому геокодирование нужно использовать бережно.
- Resend требует корректного отправителя и API key.
- Текущие роли простые, без полноценной модели прав и владения заказами.

## 13. Ближайшее развитие
- Привязать заказ к заказчику и сделать раздел "Мои заказы".
- Улучшить список заказов: фильтры, цветные статусы, карточки.
- Добавить историю изменения статусов.
- Подготовить переход с SQLite на PostgreSQL для более надежного деплоя.
- Зафиксировать основные архитектурные решения в `doc/adr.md`.
